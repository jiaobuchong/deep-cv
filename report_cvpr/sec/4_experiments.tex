\section{Experiments}
\label{sec:experiments}

\subsection{Setup}
\label{sec:setup}

\paragraph{Data and protocol.}
Validation and test labels are hidden, so we hold out 2 images per class from the training set (20,000 images, fixed seed).
We use this holdout to choose models and run ablations, and train on the other 43 images per class.
The final full fine-tuning model is then retrained on all 45 images per class; the final LoRA model keeps the holdout split and is trained on 43.
Validation and test images are used only to make submission files.
CodaBench reports top-1 accuracy; the validation set is balanced (5 images per class), so this is also the mean per-class accuracy.
Our holdout is close to the server score: 72.31\% \vs 72.57\% for full fine-tuning and 71.98\% \vs 71.90\% for LoRA.
At about 72\% accuracy on 20,000 images, the standard error is $\sqrt{0.72 \cdot 0.28 / 20{,}000} \approx 0.32$ points, so we treat differences below about 0.3 points as noise.
All runs use one seed.

\paragraph{Metrics.}
Latency is the mean time of 100 forward passes of a random $224 \times 224$ input at batch size 1, after 10 warm-up passes, with bf16 autocast on an A100.
Throughput is measured at batch size 256.
For the same model, latency varies by up to about 0.5\,ms between runs.
GPU-hours come from the clock in \cref{sec:budget}.
Peak VRAM is the most memory PyTorch allocated during training; the memory PyTorch reserved is 0.2--1.4\,GB higher (20.1\,GB for the final model).
The appendix gives training-log excerpts with time and VRAM (\cref{sec:logs}), all runs (\cref{tab:all-runs}), the hyperparameters (\cref{tab:hparams}) and the hardware and software (\cref{sec:hardware}).
All runs use one A100-SXM4-80GB, except one ablation batch whose accuracies we checked to be comparable (\cref{sec:hardware}).

The ideas that failed were useful too.

Halving it changed nothing, so we looked at the head next, which gave the largest gain of the project (\cref{sec:ablation-head}).

\Cref{tab:main} gives all four required metrics for the key models.
Our final full fine-tuning model reaches \textbf{76.22\%} on the CodaBench validation set, 5.4 points above the reference.
It uses 1.03 GPU-hours, 18.9\,GB of memory and the unchanged ViT-B/16 architecture.
Changing one setting at a time (\cref{fig:progression} in the appendix), flip TTA adds 0.27 points (it changes 4.6\% of the predictions and doubles latency), training on all 45 images per class adds 0.26 points (close to the noise, but in the expected direction), and replacing the LP head with the prototype head adds \textbf{3.12 points}.
Our final LoRA model, on all linear layers with a prototype head, reaches \textbf{71.90\%} ($+$3.6 over the reference LoRA).
It trains 1.375\% of the backbone, and after merging it has the same latency as the base model.
The two final models were not trained the same way: the LoRA model keeps the holdout split and uses no TTA.
For a fair comparison, under the same settings (3 epochs, prototype head, holdout) LoRA reaches 98\% of the full fine-tuning accuracy (71.98\% \vs 73.38\%).
On the hidden test set (Phase 2), the two final models reach \textbf{76.09\%} and \textbf{71.67\%}, within 0.25 points of their validation scores.
Both models were fixed before the test set was released, and each used one of our two Phase 2 submissions.

The project description lists several ways to adapt the backbone.
To compare them fairly, we ran seven methods with the same protocol: the prototype head (\cref{sec:head-init}), 3 epochs, the same holdout split and the same GPU (\cref{tab:compare,fig:params}).
All efficient methods use learning rate $10^{-3}$; we did not tune it for each method.

\paragraph{Where to train.}
Small changes in every block give much more accuracy per parameter than fine-tuning the top blocks.
BitFit trains 0.12\% of the backbone and beats fine-tuning the last block (8.3\%) by 1.8 points; LoRA (1.375\%) matches the last four blocks (33\%), and the Adapter (1.387\%) beats the last two (16.5\%).
Each extra top block helps less: the first block adds 6.0 points over the linear probe, the second 3.0, and each further pair about 1; six blocks come within 0.5 points of full fine-tuning.
A likely reason is that frozen lower blocks cannot change their features for the new classes, while small changes in every block reach all of them.
Among the efficient methods, LoRA is the most accurate (71.98\%), followed by the Adapter (71.54\%), AdaptFormer (71.17\%) and BitFit (69.81\%).
But LoRA is only 0.44 points ahead of the Adapter, close to our noise level; its clear advantage is that it can be merged.
The serial Adapter and the parallel AdaptFormer differ by 0.37 points, and they also use different scales (1.0 \vs 0.1), so we cannot say which placement is better.
None of these methods reaches full fine-tuning (73.38\%), although the project description expects parameter-efficient methods to do better on small data.
One possible reason: each class has few images, but the whole training set has 450,000, which is enough to fine-tune the full backbone.

\paragraph{Training memory.}
Training memory depends on how far back the gradients have to go, not on how many parameters are trained (\cref{fig:params}, right).
Partial fine-tuning adds about 1.5\,GB per trained block (4.1, 7.0 and 10.0\,GB for $K = 2, 4, 6$); for all 12 blocks this gives 18.8\,GB, the same as full fine-tuning (18.9\,GB).
BitFit and the two adapters train at most 1.4\% of the backbone but need 12.7--12.8\,GB, more than fine-tuning half the network, because their gradients must reach the first block.
They still use a third less memory than full fine-tuning and train 24--32\% faster (1,407--1,509 \vs 1,139 img/s), since frozen weight matrices need no weight gradients.
LoRA is the exception (19.9\,GB, 888 img/s; \cref{sec:ablation-peft}).
At inference, only the two adapters cost extra: 9.74 and 10.23\,ms at batch size 1, against 7.33\,ms for the plain model.

\Cref{tab:head} compares the three head starts in four settings.
In all four, the LP head is clearly the worst, 2.1--3.1 points below the prototype head.
For LoRA, the random and prototype heads end up level (71.95\% \vs 72.00\%), but the prototype head learns faster: it is 5 points ahead after the first epoch (63.3\% \vs 58.4\%).
\Cref{fig:head-curves} shows that the LP head is 18 points better before training and worse after it.

Why does the LP head hurt?
The probe was trained on \emph{the same images that are then used for fine-tuning}, so it already fits them well.
Over the first 100 steps of the LoRA runs, the mean training loss is 2.29 with the LP head, against 4.39 with the prototype head and 9.28 with a random head.
So the backbone gets only a small training signal, mostly from the few images the probe gets wrong.
When the features start to change, the trained head no longer matches them: in the LoRA run with the LP head, the training loss goes up from 2.22 to 2.69 during the first epoch, before any image is seen twice.
\Cref{fig:loss} shows the same for full fine-tuning: with the same settings, the LP model reaches a lower training loss but a much lower validation accuracy, so it memorizes more and generalizes less.
The same holds for every pair in \cref{tab:head}; for AdaptFormer, the LP run ends at a training loss of 1.86 \vs 1.98 and a holdout accuracy of 69.05\% \vs 71.17\%.
The random head is our control: it knows nothing about the classes, yet it does as well as the prototype head.
So the prototype head is not special; what hurts is a head that was trained on the training images.
LP-FT~\cite{kumar2022lpft} uses the probe so that a random head does not distort the pretrained features, mainly to keep accuracy on new domains.
In our task the features have to change, and a random head did no harm.

\subsection{Ablation: where to put PEFT capacity}
\label{sec:ablation-peft}

\Cref{tab:peft} in the appendix compares PEFT variants with the LP head for 3 epochs.
Capacity mattered more than the learning rate.
Halving the LoRA learning rate changed nothing (\minus0.12, within noise).
Adding LoRA to all four linear layers instead of only \texttt{qkv}, so that the MLP is adapted too, added 0.88 points; the MLP holds two thirds of the weights in each block.
This is still far below the 5\% that the project description gives as an example of a small set of parameters.
Merging matters for deployment: AdaptFormer is close in accuracy, but its side branches cannot be merged, so batch-1 latency rises from about 7.3\,ms to 9.89\,ms ($+$35\%).
LoRA is not cheaper to train here.
LoRA on all linear layers trains \emph{slower} than full fine-tuning (885 \vs 1,131 img/s) and needs slightly more memory (19.9 \vs 18.9\,GB).
To train its $A$ matrices, LoRA must store the input of every linear layer, as full fine-tuning does.
On top of that come the activations of its 96 extra small matrix products, which probably outweigh the about 1\,GB of weight gradients and optimizer state that full fine-tuning adds.
LoRA saves trainable parameters, optimizer state and checkpoint size (35.5\,MB, of which 30.8\,MB is the head, \vs 374\,MB).
The adapters and BitFit, in contrast, train faster and with a third less memory than full fine-tuning (\cref{sec:compare}).

\subsection{Ablation: training length}
\label{sec:ablation-length}

Full fine-tuning and LoRA react to longer training in opposite ways (\cref{tab:length} in the appendix).
Full fine-tuning keeps getting better: going from 3 to 8 epochs adds 2.21 points for the final recipe.
LoRA stops improving after about 3 epochs, and with the prototype head 6 epochs are worse than 3, although its training loss keeps falling (1.95 to 1.70).
We think the head is the cause: it holds 7.69M of LoRA's 8.87M trainable parameters.
Compared with full fine-tuning, our LoRA recipe trains the head with a 10$\times$ higher learning rate, a 500$\times$ smaller weight decay and no drop path, so with more epochs it mostly memorizes the 43 images per class.
A 6-epoch LoRA run with a head learning rate of $10^{-4}$ would test this; we have not run it yet.
So our final LoRA model uses 3 epochs (0.54 GPU-hours) and our final full fine-tuning model uses 8 epochs (1.03 GPU-hours), both within the 1.2-hour budget.

After the deadline, the gap to the top teams on the leaderboard made us ask what still limits our models.
We kept the backbone and the protocol of \cref{tab:compare} and changed only the image size.
timm interpolates the $14{\times}14$ position embeddings to the patch grid of the input ($18{\times}18$ at 288 pixels), so no parameter is added (\cref{tab:res}).
Testing our 224-pixel model at 288 pixels adds 2.1 points with no retraining.
FixRes~\cite{touvron2019fixres} explains this: random-resized crops make objects look larger during training, so slightly larger test images match them better.
Training at 288 pixels adds another 2.3 points, and the best test size moves up to 320 pixels: 77.78\%, 4.4 points above the 224-pixel model.
This 3-epoch run fits the budget: 0.68 GPU-hours and 30.2\,GB, against 0.48 GPU-hours and 18.9\,GB at 224 pixels, because a 288-pixel image has 325 tokens instead of 197.
We also trained the full 8-epoch recipe at 288 pixels on all images; it takes 1.61 GPU-hours, over the budget, and has no test score, so it is not one of our results.
Input resolution gave the largest gain we found, but we found it too late.
